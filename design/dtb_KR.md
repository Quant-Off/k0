# 신뢰하지 않는 입력으로서의 디바이스 트리

[English](dtb.md)

부트로더는 K0에 머신을 설명하는 flattened 디바이스 트리(DTB)를 넘깁니다. RAM이 얼마나 어디에 있는지, 펌웨어가 어떤 구간을 예약했는지, 부팅 엔트로피 일부가 들어 있습니다. K0는 이 블롭을 적대적 입력으로 취급합니다. 이 문서는 그 이유, 파서가 읽는 내용, 테스트 방법을 설명합니다. 파서는 `crates/k0-boot/src/fdt.rs`에 있습니다.

## DTB를 신뢰하지 않는 이유

많은 플랫폼에서 DTB는 커널 이미지와 같은 곳에서 오지 않습니다. 서명된 커널 옆의 별도 파일일 수도 있고, 펌웨어가 적용한 오버레이일 수도 있으며, 부트로더가 점프 직전에 수정하는 블롭일 수도 있습니다. 따라서 정상적인 커널도 잘못되었거나 적대적인 DTB를 받을 수 있습니다. K0는 그럴 수 있다고 가정합니다.

파서는 하나의 원칙을 따릅니다. DTB의 값은 커널이 부팅을 거부하게 하거나 더 적은 자원을 갖게 할 수는 있지만, 하드웨어가 실제로 제공하는 것보다 더 많은 권한을 부여해서는 안 됩니다.

- **예약 구간은 메모리를 제거할 뿐입니다.** 적대적인 예약이 할 수 있는 일은 사용자 공간에 넘기는 메모리를 줄이는 것이 최대입니다.
- **엔트로피는 여러 입력 중 하나일 뿐입니다.** `/chosen`의 바이트는 SHA-256을 통해 다른 소스와 섞이므로, 적대적인 엔트로피로 PAC 키를 약화할 수 없습니다. 시드가 없으면 키의 품질이 낮아지며, 커널은 부팅 로그에 이를 알립니다([hardening_KR.md](hardening_KR.md) 참고).
- **메모리 노드는 메모리를 부여하므로 가장 엄격하게 검사합니다.** 모든 메모리 리전은 사용자 공간이 매핑할 수 있는 untyped 메모리가 됩니다. RAM이라고 주장하지만 실제로는 디바이스를 덮는 리전은 EL0에 그 디바이스 직접 접근을 넘기게 됩니다. 파싱 후 커널은 모든 메모리 리전을 자신의 MMIO 윈도우(UART와, QEMU에서는 GIC)와 비교하고, 겹치면 부팅을 중단합니다. CNode bootstrap도 서로 겹치는 메모리 리전을 거부하므로 어떤 프레임도 두 번 retype될 수 없습니다.

## 두 단계

MMU가 켜진 상태에서 커널이 블롭을 읽으려면 먼저 매핑해야 하고, 전체 파싱에는 higher-half로 점프한 뒤에야 동작하는 재배치된 데이터가 필요합니다([boot_KR.md](boot_KR.md) 참고). 그래서 파서는 두 단계로 실행됩니다.

**`dtb_span`, MMU가 켜지기 전.** `x0`의 물리 주소에서 첫 8바이트만 읽습니다. 주소는 null이 아니어야 하고 8바이트로 정렬되어 있어야 합니다. 매직은 `0xd00dfeed`여야 합니다. 전체 크기는 40바이트(헤더 하나)에서 2 MiB 사이여야 합니다. 상한은 DTB 매핑이 소비할 수 있는 페이지 테이블 수를 제한합니다. 결과는 `enable_paging`이 읽기 전용으로 매핑하는 물리 구간입니다.

**`parse`, 점프 이후.** 커널 별칭을 통해 읽지만 물리 주소를 보고합니다. 별칭 주소에서 `dtb_span`을 다시 실행하고, 물리 구간이 커널 이미지와 겹치면 블롭을 거부합니다. 그다음 정확히 전체 크기만큼의 바이트 슬라이스를 만들어 `parse_blob`에 넘깁니다. 이 시점부터 모든 접근은 safe Rust의 경계 검사된 슬라이스 접근이고, 모든 오프셋 계산은 checked 산술을 씁니다. 잘못된 블롭은 `parse_blob`이 에러를 반환하게 만들 수는 있지만, 슬라이스 밖을 읽게 만들 수는 없습니다.

## 파서가 읽는 내용

헤더는 버전 17 이상을 알려야 하고 버전 17과 하위 호환이어야 합니다. 구조 블록은 4바이트 경계에서 시작해야 하며 크기가 4의 배수여야 합니다. 구조 블록과 문자열 블록은 모두 블롭 안에서 끝나야 합니다.

파서는 정확히 다음 항목만 읽고 그 외는 건너뜁니다.

| 소스 | 항목 |
| --- | --- |
| memory reservation block | 종결 `(0, 0)` 쌍까지의 `(address, size)` 쌍. 크기가 0인 쌍은 건너뜁니다. 블록은 8바이트로 정렬되어야 합니다. |
| 루트 노드 | `#address-cells`와 `#size-cells`. 기본값은 2와 1입니다. 1과 2만 지원합니다. |
| 최상위 `memory` 또는 `memory@...` 노드 | `reg`. 루트의 셀 크기로 디코딩합니다. |
| `/reserved-memory`의 자식 노드 | `reg`. `/reserved-memory` 자체의 셀 크기로 디코딩합니다. |
| `/chosen` | `rng-seed`와 `kaslr-seed`. 이어 붙여 72바이트로 제한합니다. |

다른 깊이에 있는 같은 이름의 노드는 무시합니다. `/soc` 안의 `memory`라는 노드는 RAM이 아닙니다. 크기만 주고 `reg`가 없는 reserved-memory 자식 노드는 펌웨어가 주소에 고정하지 않은 동적 할당이므로 역시 무시합니다.

고정된 제한이 파서 자체의 상태를 작고 정적으로 유지합니다.

| 제한 | 값 |
| --- | --- |
| 전체 크기 | 2 MiB |
| 중첩 깊이 | 32 |
| 메모리 리전 | 8 |
| 예약 리전, 두 소스 합산 | 8 |
| 엔트로피 바이트 | 72 |

## 무엇이 에러인가

모든 위반은 `BootError`를 반환하고, 커널은 `k0: dtb rejected: ...`를 출력한 뒤 파킹합니다. 에러는 다음을 포함합니다.

- 잘못된 매직, 정렬, 크기, 버전, 헤더 오프셋
- 알 수 없는 토큰, 깊이 0에서의 end-node 토큰, 노드 밖의 프로퍼티, 이름이 있는 루트 노드, 종결 0 바이트가 없는 노드 이름, end 토큰 전에 끝나는 구조 블록
- 문자열 블록 밖을 가리키는 프로퍼티 이름 오프셋, 종결 0 바이트가 없는 이름
- 구조 블록을 넘어가는 프로퍼티 값
- 지원하지 않는 셀 크기, 또는 정확히 4바이트가 아닌 셀 크기 프로퍼티
- 비어 있거나 엔트리의 정수 배가 아닌 `reg` 값
- 베이스에 크기를 더하면 64비트를 넘는 모든 리전
- 제한보다 많은 리전
- 메모리가 전혀 없는 경우

## 테스트 방법

파서는 바이트 슬라이스에 대한 순수 로직이므로 호스트에서 테스트합니다.

- **단위 테스트**(`crates/k0-boot/src/fdt/tests.rs`)는 위의 각 규칙을 다룹니다. 원시 포인터를 통해 제자리에서 실행하는 헤더 검사, 커널 이미지와의 겹침 검사, 별칭을 통해 읽는 경로를 포함합니다.
- **모델.** 테스트 전용 빌더(`fdt/builder.rs`)가 보드의 간단한 설명으로 DTB를 작성하고 파서가 반환해야 할 값을 계산합니다. 많은 단위 테스트가 손으로 쓴 값이 아니라 이 모델과 파서의 출력을 비교합니다.
- **결정적 변이 퍼저**(`fdt/fuzz.rs`). 각 케이스는 무작위 보드를 생성하고, 무작위의 무관한 노드, 프로퍼티, `NOP` 토큰으로 감싼 뒤, 파싱 결과를 모델과 대조합니다. 그다음 비트 플립, 헤더 필드 재작성, 잘라내기, 이어 붙이기, 토큰 삽입 같은 변이를 최대 네 번 적용하고, 결과를 두 번 파싱합니다. 한 번은 슬라이스로, 한 번은 0으로 채운 2 MiB 버퍼가 받치는 원시 포인터 진입점을 통해서입니다. 패닉이 발생하면 테스트가 실패합니다. 수락된 결과는 위 표의 모든 제한을 지켜야 합니다. 이 퍼저는 추가 크레이트가 필요 없고 완전히 오프라인으로 실행되지만, 커버리지 피드백은 없습니다.

기본 테스트 실행은 20,000개의 케이스를 실행합니다. CI는 매주 새 시드로 500만 개의 케이스를 실행합니다. 이 문서를 작성한 시점에 각 500만 케이스씩 다섯 번의 캠페인에서 파서 실패는 발견되지 않았습니다. 퍼저가 보고한 유일한 실패는 테스트 모델 자체에 있었고, 모델은 `(0, 0)` 쌍이 memory reservation block을 끝낸다는 사실을 알지 못했습니다.

## 알려진 공백

- 리전 주소는 CPU의 물리 주소 폭에 대해 검사하지 않습니다. 구현된 범위보다 높은 곳에 RAM을 선언하는 DTB는 부팅 중이나 이후 retype 중에 커널을 패닉시킬 수 있습니다. 이것이 [SECURITY_KR.md](../SECURITY_KR.md)의 어드바이저리 GHSA-hj3f-38h9-hrpj입니다. 영향은 DTB를 제어하는 쪽에 의한 서비스 거부입니다.
- MMIO 겹침 검사는 커널이 스스로 매핑하는 윈도우만 압니다. 다른 디바이스 구간을 RAM으로 기술하는 DTB는 잡아내지 못합니다. 커널에 독립적인 디바이스 목록이 없기 때문입니다.
