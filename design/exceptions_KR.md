# 예외, 시스템 콜, 폴트 격리

[English](exceptions.md)

이양 이후 커널 코드는 예외에 응답할 때만 실행됩니다. 이 문서는 벡터 테이블, 사용자 상태를 저장하고 복원하는 방법, 시스템 콜을 디스패치하는 방법, 폴트를 일으킨 태스크를 격리하는 방법을 설명합니다. 코드는 `crates/k0-arch/src/vectors.S`, `vectors.rs`, `usermode.rs`, `irq.rs`, 그리고 `kernel/src/main.rs`의 `k0_syscall`, `k0_fault`, `k0_preempt`에 있습니다.

## 메커니즘과 정책

`k0-arch`는 메커니즘을 담당합니다. 레지스터 저장, 예외 디코딩, 인터럽트 확인이 여기에 해당합니다. 결정은 커널 바이너리에 있습니다. `k0-arch`는 외부 함수 `k0_syscall`, `k0_fault`, `k0_preempt` 세 개를 선언하고, 커널 바이너리가 이를 정의합니다. 따라서 태스크에 영향을 주는 모든 정책은 `kernel/src/main.rs` 한 파일에 있습니다.

## 벡터 테이블

AArch64는 벡터 엔트리를 16개 가집니다. 4가지 발생 위치마다 예외 종류(동기, IRQ, FIQ, SError)가 4개씩입니다. K0는 각 엔트리에 세 가지 동작 중 하나를 부여합니다.

| 발생 위치 | 동기 | IRQ | FIQ | SError |
| --- | --- | --- | --- | --- |
| `SP_EL0`을 쓰는 EL1 | fatal | fatal | fatal | fatal |
| `SP_EL1`을 쓰는 EL1 | fatal | 처리 후 복귀 | 처리 후 복귀 | fatal |
| EL0, AArch64 | 저장, 처리 후 복귀 | 저장, 처리 후 복귀 | 저장, 처리 후 복귀 | fatal |
| EL0, AArch32 | fatal | fatal | fatal | fatal |

커널은 항상 `SP_EL1`에서만 실행되므로 `SP_EL0` 행은 발생하지 않아야 합니다. K0는 32비트 코드를 실행하지 않습니다. SError는 하드웨어가 비동기 오류를 보고했다는 뜻이며, 커널은 이를 복구하려고 하지 않습니다.

### 치명적 경로

fatal 엔트리는 스택 포인터를 신뢰하지 않습니다. 폴트가 스택 오버플로일 수 있기 때문입니다. 전용 8 KiB 예외 스택으로 전환한 뒤 `exception_fatal`을 호출합니다. 이 함수는 벡터 종류, 예외 클래스를 디코딩한 `ESR_EL1`, `ELR_EL1`, `FAR_EL1`, `SPSR_EL1`을 출력하고 코어를 파킹합니다. 출력은 raw 문자열과 16진수 출력만 사용하므로 higher-half로 점프하기 전의 폴트에서도 동작합니다.

### 커널 안에서 발생한 인터럽트

EL1에서 받은 IRQ나 FIQ는 caller-saved 레지스터를 커널 스택에 저장하고, 핸들러를 호출한 뒤 복귀합니다. 이양 이후에는 이 경로가 발생하지 않습니다. 예외 진입이 인터럽트를 마스크하고, 커널이 예외를 처리하는 동안 마스크를 해제하지 않기 때문입니다. 커널 자체는 선점되지 않습니다.

## 사용자 상태 저장과 복원

예외가 EL0에서 도착하면 진입 스텁은 `x0`과 `x1`을 커널 스택에 저장하고, 핸들러의 주소와 함께 `__lower_common`으로 점프합니다. `__lower_common`은 전역 포인터 `__current_context`를 로드합니다. 이 포인터는 항상 현재 태스크의 TCB 안에 있는 저장 컨텍스트를 가리키며, 사용자 상태 전체가 여기에 저장됩니다.

| 오프셋 | 내용 |
| --- | --- |
| 0부터 240 | `x0`부터 `x30` |
| 248 | `SP_EL0`, 사용자 스택 포인터 |
| 256 | `ELR_EL1`, 사용자 프로그램 카운터 |
| 264 | `SPSR_EL1`, 사용자 프로세서 상태 |
| 272 | `TPIDR_EL0` |
| 280 | `TPIDRRO_EL0` |

스레드 포인터 레지스터도 함께 저장하므로, 한 태스크의 스레드 포인터가 다른 태스크에 나타나는 일은 없습니다. Rust `Context` 구조체는 이 오프셋과 정확히 일치해야 합니다. `usermode.rs`의 컴파일 타임 assertion이 모든 필드 오프셋과 전체 크기 288바이트를 검사하므로, 불일치하면 빌드가 실패합니다.

핸들러는 이 컨텍스트에 대한 가변 참조를 받으며 컨텍스트를 바꿀 수 있습니다. 반환값을 쓰거나, 프로그램 카운터를 진행시키거나, `__current_context`가 다른 태스크를 가리키게 할 수 있습니다. 핸들러가 반환하면 실행은 `__user_restore`로 이어지고, 여기서 `__current_context`를 다시 로드해 그 포인터가 가리키는 컨텍스트로 사용자 상태를 복원합니다. 그래서 태스크 전환은 포인터 변경일 뿐입니다([scheduling_KR.md](scheduling_KR.md) 참고). 이양 때 EL0로 처음 진입하는 경로도 같은 복원 경로를 씁니다.

FP/SIMD 레지스터는 컨텍스트에 포함되지 않습니다. EL0의 모든 FP/SIMD 명령이 트랩되므로 포함할 필요가 없습니다([hardening_KR.md](hardening_KR.md) 참고).

## EL0의 동기 예외

`el0_sync`는 `ESR_EL1`을 읽고 예외 클래스에 따라 처리합니다.

- **AArch64의 `SVC`** 는 `k0_syscall`로 갑니다. CPU가 이미 반환 주소를 `svc` 다음 명령으로 설정해 두었습니다.
- **트랩된 `WFI` 또는 `WFE`** 는 건너뜁니다. 반환 주소를 그 명령 뒤로 옮기고 태스크는 계속 실행됩니다.
- **그 외 전부** 는 폴트입니다. abort, 정의되지 않은 명령, 트랩된 시스템 레지스터 접근, FP/SIMD 사용, 정렬 폴트, `brk` 등이 여기에 속합니다. 이들은 `FAR_EL1`과 함께 `k0_fault`로 갑니다.

## 시스템 콜

시스템 콜 번호는 `x8`에 있습니다. 인자는 `x0`부터 `x5`까지이고, 결과는 `x0`으로 돌아옵니다. IPC 수신 호출은 `x1`부터 `x5`로도 데이터를 반환합니다. 오류는 음수 값입니다(`k0_abi::err` 참고).

| 번호 | 호출 | 설명 |
| --- | --- | --- |
| 0 | `DEBUG_PUTC` | 필터를 거친 바이트 하나를 콘솔에 출력 |
| 1 | `YIELD` | 준비 큐의 맨 뒤로 이동 |
| 2 | `EXIT` | 호출한 태스크 종료 |
| 3 | `RETYPE` | untyped 메모리에서 커널 오브젝트 생성 |
| 4 | `MAP` | 프레임 매핑 또는 페이지 테이블 설치 |
| 5 | `TCB_CONFIGURE` | 새 태스크의 진입점, 스택, 주소 공간 설정 |
| 6 | `TCB_RESUME` | 구성을 마친 태스크 시작 |
| 7 | `SEND` | 메시지 송신 |
| 8 | `RECV` | 메시지 수신 |
| 9 | `CALL` | 송신 후 응답 대기 |
| 10 | `REPLY_RECV` | 응답한 뒤 다음 메시지 수신 |

알 수 없는 번호는 단순한 오류 코드로 끝나지 않습니다. K0는 이를 태스크가 손상되었거나 악의적이라는 신호로 보고, `k0: unknown syscall N, killing task`를 출력한 뒤 호출자를 종료합니다.

## 폴트 격리

EL0의 폴트는 시스템이 아니라 폴트를 일으킨 태스크의 문제입니다. `k0_fault`는 진단 라인 하나를 출력합니다.

```
k0: task fault dabort-lower (esr 0x92000046 elr 0x400398 far 0x0), killing task
```

그런 다음 `kill_current`를 호출하며, 이 함수는 두 가지를 순서대로 수행합니다.

1. 태스크가 가진 응답 자격을 회수합니다. 그 응답을 기다리던 태스크는 `NO_REPLY`와 함께 깨어납니다([ipc_KR.md](ipc_KR.md) 참고).
2. 태스크를 `Dead`로 표시하고 다음 준비 태스크로 전환합니다.

죽은 태스크가 마지막 실행 가능 태스크였다면 커널은 `k0: all tasks exited`를 출력하고 파킹합니다.

## EL0의 타이머 인터럽트

EL0에서 받은 IRQ(QEMU) 또는 FIQ(Apple Silicon)는 시스템 콜과 같은 방식으로 저장됩니다. 핸들러는 인터럽트를 확인합니다. 타이머였다면 타이머를 1초 뒤로 다시 설정하고 `k0: tick N`을 출력한 뒤 `k0_preempt`를 호출하며, 이 함수가 다음 준비 태스크로 순환합니다. 1020부터 1023까지의 가짜 인터럽트 번호는 무시합니다. 그 외의 인터럽트 번호, Apple Silicon의 IRQ, QEMU의 FIQ는 설계상 발생할 수 없으므로 커널은 `k0: UNEXPECTED ...`를 출력하고 파킹합니다.

## 테스트 방법

루트 태스크 자가 테스트는 널 포인터에 쓰는 태스크 하나와 FP/SIMD 명령을 실행하는 태스크 하나를 시작합니다. 두 태스크가 각각 종료되는지, 폴트를 일으킨 명령 뒤의 코드가 실행되지 않는지, 루트 태스크와 다른 태스크가 계속 실행되는지 검사합니다. 스레드 포인터 레지스터가 태스크별로 분리되어 있는지도 검사합니다. `tools/qemu-boot-test.sh`는 폴트 라인 `k0: task fault dabort-lower`와 `k0: task fault fp-simd` 두 개를 모두 요구하고, 이어서 `root: fault isolation tests pass`가 나오기를 요구합니다.

## 알려진 공백

- 폴트를 일으킨 태스크는 항상 종료됩니다. 페이저나 감독자가 대응할 수 있도록 폴트를 IPC로 핸들러 태스크에 전달하는 기능은 계획되어 있지만 구현되어 있지 않습니다.
- 인터럽트를 제외한 EL1의 모든 예외는 치명적입니다. 커널은 자신의 폴트를 복구하지 않습니다.
- 폴트 메시지에는 사용자 주소가 포함됩니다. 디버깅에는 유용하지만, 모든 태스크가 쓸 수 있는 콘솔로 출력됩니다.
