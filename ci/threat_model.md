# Threat model: K0

K0 is a capability-based microkernel for AArch64, written in Rust `no_std` in the style of seL4 and licensed under PolyForm Noncommercial 1.0.0. The kernel runs at EL1. The user-space code is the root task, which runs at EL0 and doubles as the self-test harness, and the vault and terminal tasks that it starts in images built with those features. Console output is optional: it exists only in an image built with a console feature (see "Optional console output" in `SECURITY.md`). Serial input and the operator terminal are optional too: they exist only in an image built with the feature `console-input` or `terminal`, and an image without them has no input code at all (see "Serial input and the operator terminal" in `SECURITY.md`). One generic image finds the console, the interrupt controller (GICv2 or GICv3) and the timer in the device tree at boot, and it may be entered at EL1 or at EL2. The 4 KiB granule is the default and the 16 KiB granule is a build option. It can also be started by a UEFI loader (`loader/`) that embeds the kernel. Only QEMU machines can be exercised in this image, with the EDK2 firmware package installed for the loader.

Read `SECURITY.md` at the repository root first. It describes the isolation model of the released version 0.1.0, the unreleased isolation work on the current `main` branch, and the issues that are already known. This model describes the current `main` branch.

## What the kernel does and where untrusted input enters

Trust boundaries, from least to most trusted:

1. **EL0 code via system calls (`svc`).** Every register a task passes to the kernel is attacker controlled: capability slot indices, virtual addresses, permission bits, sizes, object types, badges and message words. This is the primary attack surface. Entry path: `crates/k0-arch/src/vectors.S` (`__lower_common`) -> `crates/k0-arch/src/usermode.rs` (`el0_sync`) -> `kernel/src/syscall.rs` (`k0_syscall` and the `sys_*` functions). Slot arguments are resolved only in the calling task's own CNode.
2. **EL0 faults.** Data and instruction aborts, undefined instructions, trapped system register and FP/SIMD accesses, `brk` and alignment faults all reach `k0_fault` in `kernel/src/syscall.rs`, which must only kill the faulting task.
3. **Timer interrupts** taken at EL1 and from EL0 (`irq_current`, `irq_lower`), which drive preemption in `crates/k0-sched` (the decision whether a tick cuts the running task is `crates/k0-slice`, called through `on_tick`) and the expiry of IPC timeouts (`k0_ipc::expire_timeouts`, run on every tick, also from the idle loop).
4. **The device tree blob (DTB)** that the boot chain passes in `x0`. Nothing reads it before the MMU is on. `kernel_main` in `kernel/src/main.rs` maps it read-only (`map_dtb`), then `crates/k0-boot/src/fdt.rs` reads the memory map and `crates/k0-boot/src/platform.rs` finds the console, the interrupt controller and the timer interrupt, both on the shared walker `crates/k0-boot/src/fdt/walk.rs`. The results become the physical memory map (`k0_cap::bootstrap`) and the device mappings, after `Platform::validate` has checked the devices against the memory map (`bring_up_platform` in `kernel/src/main.rs`). The boot chain is trusted to load an authentic kernel image, but the DTB code must still be total: no panic, no out-of-bounds read, no integer overflow on any input, and no device range that overlaps memory handed to user space.
5. **The root task image** is embedded in the kernel at build time together with its SHA-256 (`crates/k0-boot/build.rs`, `verify_root_task`). It is part of the trusted computing base today. The hash detects corruption, not a malicious image; signature verification is a documented TODO.

6. **The UEFI loader** (`loader/`, `crates/k0-efi`) sits between the firmware and the kernel, and it is in scope. Its inputs come from firmware and are treated as wrong or hostile data: the UEFI memory map, the firmware device tree or, without one, the ACPI static tables (RSDP, XSDT, MADT, GTDT, SPCR) from the configuration table, the random number protocol and the embedded kernel image. It decides which memory the kernel sees as RAM, so a mistake there hands firmware memory to user space without any kernel bug. Entry path: `loader/src/load.rs` (flow) -> `crates/k0-efi/src/prepare.rs` (plan, rewrite, self-check with the kernel's own parser, discovery, `Platform::validate` and `boot_window`) -> `loader/src/handoff.rs` (cache flush, MMU off, jump). The pure logic is in `memmap.rs`, `fdtw.rs`, `verify.rs` and `image.rs` of `k0-efi`, none of it `unsafe`. The loader does not verify a signature: its SHA-256 over the embedded kernel is a corruption check, and authenticity is the firmware's Secure Boot job.
7. **The vault task and its clients** (optional, features `vault` and `vault-ed25519` of `k0-kernel`). The vault holds one Ed25519 key in its own address space. Clients send requests over one endpoint with a badge that the kernel delivers; the badge selects the role (admin, operator, signer, reader) in a policy fixed at build time. The operator is the terminal of boundary 8. Everything in a request (operation, algorithm, length, message, nonce) is attacker controlled, and the vault reads the body once into a private buffer. The root task builds the vault and is trusted, so a root task that reads the vault is not a finding. Entry path: `userspace/k0-vault` (`server`, `proto`, `provider`) and the wiring and self-test in `userspace/root-task/src/oracle.rs`. The Ed25519 code is the vendored crate `ed25519-dalek` 2.2.0, which has no validation of any kind.
8. **The serial line and the operator terminal** (optional, features `console-input` and `terminal` of `k0-kernel`). Every byte that arrives on the console UART is attacker controlled, and so is its timing. The kernel's receive path runs at EL1 in interrupt context: it puts bytes into a ring of 256 bytes and never interprets them, and the console interrupt is the second interrupt source after the timer. `CONSOLE_READ` hands one byte at a time to the one task that holds a `Console` capability with the read right (R). The terminal task (`userspace/k0-term`) parses lines in its own address space and, when the vault is built in, acts as the vault's operator: it can ask for `STATUS`, `PUBLIC_KEY`, `KEYGEN` and `ZEROIZE`, nothing else. There is no authentication on the serial line, so whoever reaches it is the operator, and erasing the key is a denial of service by design. Entry path: `crates/k0-arch/src/conin.rs` and `crates/k0-conin` (receive logic), `crates/k0-ipc/src/console.rs` and `kernel/src/syscall.rs` (`CONSOLE_READ`, the rights of `Console`), `userspace/k0-term` (`lib.rs`, `wire.rs`) and its wiring in `userspace/root-task/src/oracle.rs`. The interrupt number comes from the device tree or the ACPI SPCR table, which are inputs of boundary 4 and 6.

Out of the kernel's control and therefore trusted: the rest of the boot chain (firmware, any other boot loader, the hypervisor), the integrity of the kernel image itself, and the hardware. Under UEFI the firmware is trusted to run honestly, but the loader must still not trust what it describes.

## Components that matter most and least

Highest value, all in scope:

- `kernel/src/syscall.rs`: system call dispatch, every capability lookup and permission check, `k0_fault`, the exit path that handles a task that died during its own call.
- `kernel/src/object.rs` and `kernel/src/main.rs`: object creation and finalization, `write_bootinfo`, platform bring-up and the choice of the boot frame window.
- `crates/k0-cap`: CNode objects, the derivation list, `Untyped` accounting and `retype`, copy, move, delete and revoke, finalization without recursion, bootstrap of the memory regions.
- `crates/k0-mm`: page table construction, the table pool (`Pool::map_page` and its rollback), the boot-time reserve of alias tables and address space entries (`alias_tables_for`, `reserve_tables`), W^X enforcement, user mapping validation, the user page table walkers and the address space registry (id and generation per address space, stale mapping records).
- `crates/k0-arch`: exception vectors and user context save/restore (`vectors.S`, `usermode.rs`), hardening (`hardening.rs`: PAC, BTI, PAN, `CPACR_EL1`), the GICv2 and GICv3 drivers and the timer (`irq.rs`), the console drivers and the boot log (`earlycon.rs`, `earlycon/uart.rs`), cache and TLB maintenance. The entry code and the EL2 setup are in `kernel/src/arch/aarch64/boot.S`.
- `crates/k0-ipc`: endpoint state machine, send, receive, call, reply, `abort_reply`.
- `crates/k0-sched` and `crates/k0-task`: run queue, `kill_current`, TCB state, the list of timed waiters (`arm_timeout`, `disarm_timeout`, `expired`).
- `crates/k0-boot`: FDT walker and memory parser, platform discovery and validation (`platform.rs`), the boot window search (`boot_window` in `window.rs`, shared by the kernel and the loader), root task flattening and verification at build time and at boot.
- `crates/k0-abi`: system call numbers and ABI structures shared with user space.
- `crates/k0-efi` and `loader/`: the memory policy (`memmap.rs`: only `EfiConventionalMemory`, `EfiLoaderCode` and `EfiLoaderData` with the WB attribute and without RUNTIME, SP or NV are RAM; overlaps and unknown types are not RAM; the firmware device tree's own memory nodes, reservations and discovered devices are cut out), the device tree rewriter (`fdtw.rs`), the independent verifier (`verify.rs`), the composition and self-check (`prepare.rs`), the image header check (`image.rs`), the UEFI bindings and flow (`loader/src/efi.rs`, `load.rs`), the `ExitBootServices` retry, wiping and freeing on a refusal, the entropy handling, and the cache flush, MMU-off trampoline and jump (`handoff.rs`).

- `userspace/k0-vault` and `userspace/root-task/src/oracle.rs`: the request state machine (`Vault::handle`), the badge policy, the provider boundary around the crypto crate, the entropy rule (`NO_ENTROPY`), the rights of the request and response frames, and the nonce handshake. Reports that are welcome: a key disclosed to a client, a policy bypass (an operation a role must not have), and a reply that reaches the wrong caller.

- The input path: `crates/k0-conin` (ring, drain, gate and loss marking), `crates/k0-arch/src/conin.rs` and the PL011 and SBSA receive code in `earlycon/uart.rs`, the receive interrupt handling in `irq.rs`, the `Console` rights (R and W) and the output filter, `CONSOLE_READ` and its waiter (`crates/k0-ipc/src/console.rs`), and `userspace/k0-term` with its wiring check in `oracle.rs`. Reports that are welcome: a byte stream that makes the kernel misbehave, interrupt work that is not bounded by the reader, a wake-up of the wrong task, a `Console` right that is gained instead of removed, and an operator operation beyond the four listed.

Lower value:

- `userspace/root-task` (other than `oracle.rs`): the trusted root task and test harness. Bugs here are not kernel vulnerabilities, but it is the right place to write reproducers.
- `vendor/`: third-party crates vendored with pinned checksums. Only `sha2` and its dependencies are linked into the kernel, for the boot-time hash of the fixed root task image. Report issues there only if reachable through that use; generic upstream findings are out of scope.
- `tools/qemu-virt-runner.sh`, `tools/boot-matrix.sh`, `tools/boot-log.py`, `kernel/build.rs`, `crates/k0-boot/build.rs`, `userspace/root-task/build.rs`, `loader/build.rs`, `tools/build-loader.sh`, `tools/pe-check.py`: developer tooling that runs on the trusted build host.
- Documentation, `.idea/`, `.claude/`.

## How to exercise it

- Build: `cargo build -p k0-kernel --features console --offline` (generic 4 KiB image with console, dev profile with debug info; `panic = "abort"` in every profile). Input and output are Cargo features that only add and are never in `default`, so every command names them. The operator terminal image is `cargo build -p k0-kernel --features console,terminal,vault-ed25519`, and `cargo run -p k0-kernel --features console,terminal,vault-ed25519` boots it under QEMU with the serial port on the terminal (QEMU's own escape key is Ctrl-A, so it never reaches K0 there). `tools/term-test.py <image>` boots an image with QEMU's serial port on pipes and runs a scripted session (every command and error, a line that is too long, 200 kB without a line end, 2000 lines in a row, a serial break), and `tools/qemu-boot-test.sh` takes `K0_BOOT_INPUT=on|off` and `K0_BOOT_SERVICE=vault|plain|none`. `cargo build -p k0-kernel --offline` builds an image without console: it has no UART driver, never maps the console page and prints nothing on the serial port, and `tools/qemu-boot-test.sh` cannot judge it from the serial log (it prints a hint). All feature sets write the same ELF path, so give an image without console its own directory, for example `--target-dir target/quiet`. The 16 KiB image is `cargo build -p k0-kernel --offline --no-default-features --features granule-16k,console --target-dir target/g16`. It boots only on a CPU model with 16 KiB pages: `K0_QEMU_CPU=max tools/qemu-boot-test.sh target/g16/aarch64-unknown-none-softfloat/debug/k0-kernel`. `grep -a 'k0: console drivers' <image file>` tells which I/O an image was built with.
- Run: `tools/qemu-virt-runner.sh target/aarch64-unknown-none-softfloat/debug/k0-kernel`, which is what `cargo virt` (alias of `cargo run -p k0-kernel --features console`) does. A plain `cargo run -p k0-kernel` boots the image without console, and the runner then prints `runner: this kernel has no console driver and prints nothing here (build with --features console to see output)`. It converts the ELF to a raw image with `llvm-objcopy` and boots `qemu-system-aarch64 -machine virt,gic-version=3 -cpu cortex-a72 -smp 1 -m 512M -nographic`. `K0_QEMU_MACHINE`, `K0_QEMU_CPU`, `K0_QEMU_SMP` and `K0_QEMU_MEM` change the machine, for example `K0_QEMU_MACHINE=virt,gic-version=2` or `K0_QEMU_MACHINE=virt,gic-version=3,virtualization=on` (entry at EL2). `tools/boot-matrix.sh` runs every configuration that K0 calls supported. The kernel never exits: once the root task finishes its self-tests it yields forever and an image with a console driver prints `k0: tick N` on the console once a second (every image logs only the first 4 tick lines in the boot log). Wrap every run in `timeout`, or use `tools/qemu-boot-test.sh`, which checks the expected log lines in order, requires an exact number of `k0: task fault` lines and exactly one `k0: unknown syscall` line, and stops QEMU once they appear.
- A healthy boot log is in `/src/bootcheck.log`, captured when this image was built. The lines that matter are `k0: w^x checks pass`, `k0: user w^x checks pass`, `root: retype/map tests pass`, `root: child exit test pass`, `root: ipc tests pass`, `root: fault isolation tests pass`, `root: preempt test pass`, `root: isolation tests pass`, `root: violation tests pass`, `root: teardown tests pass`, `root: timeout tests pass`, `root: revocation tests pass`, `root: kernel reserve tests pass` and `root: sched tests pass`. Every image also prints `k0: dtb seeds wiped <n>B` (40B on QEMU virt) and `root: boot seed from rng-seed bytes ...`. An image built with the feature `vault` also prints `root: oracle tests pass` and two more `k0: task fault` lines (8 instead of 6). An image built with the feature `terminal` shows two more `k0: task fault` lines than the same image without it (the hostile wiring checks: 8 in total without `vault`, 10 with it), `root: terminal wiring holds` and `root: service started`. An image with `console-input` prints `k0: console input on (pl011 irq 33)` or `k0: console input off (<reason>)` and `root: console input tests pass`. When a task first reads console input the `k0: tick N` lines stop after `k0: tick lines off (console input in use)`.
- Reproducers: the root task (`userspace/root-task/src/main.rs`) is the only EL0 image and already contains the test harness and thin `sys*` wrappers around `svc`. Add a test there; when the reproducer needs its own thread, build a task with its own CNode and address space (`RETYPE`, `TCB_CONFIGURE`, `TCB_RESUME`), which then runs code from the root task image, rebuild and run. `crates/k0-boot/build.rs` rebuilds and re-embeds the root task automatically.
- UEFI loader: `cargo build -p k0-kernel --features console --offline`, then `tools/build-loader.sh`, which embeds that kernel into the loader, prints `build-loader: embedding a kernel with: k0: console drivers [...]` so that nobody embeds a silent kernel unknowingly, and prints the path (`<kernel ELF>.efi`). `tools/qemu-virt-runner.sh <file>.efi` boots it through EDK2 with `-machine virt,gic-version=3,acpi=off` (firmware from `K0_QEMU_FIRMWARE`, else Homebrew's `edk2-aarch64-code.fd`, else `/usr/share/AAVMF/AAVMF_CODE.fd`, which is the Debian package in this image). `K0_QEMU_ESP=1` boots it from a FAT drive instead of `-kernel`, and `K0_QEMU_EXTRA` passes extra QEMU arguments. `tools/qemu-boot-test.sh <file>.efi` judges the run from the loader's first line, `k0-loader: start`, so firmware messages before it do not count. The loader prints `k0-loader: ...` lines before the kernel's, and a refusal reads `k0-loader: refused: <reason>`. `K0_QEMU_MACHINE=virt,gic-version=3` (ACPI on, no device tree) boots through the static tables. `tools/pe-check.py <file>.efi` checks the PE form and the order of the cache and MMU instructions. `K0_LOADER_FEATURES=refuse-halt tools/build-loader.sh` builds a loader that parks instead of returning to the firmware. The UEFI rows of `tools/boot-matrix.sh` (`uefi-*`) cover GICv2 and GICv3 at EL1 and EL2, the max CPU, 4 cores, the 16 KiB image, a firmware RNG, the FAT drive, the ACPI rows (`uefi-acpi-*`) and the refusals.
- Host tests: `tools/host-test.sh` runs the unit tests of `k0-abi`, `k0-cap`, `k0-boot`, `k0-efi`, `k0-conin`, `k0-slice`, `k0-vault` and `k0-term` on any host and those of `k0-mm` on AArch64 hosts. `k0-cap` includes a model test over random retype, copy, move, delete and revoke sequences, and `k0-mm` runs the real user page table walkers and the address space registry. The DTB parser has a deterministic mutation fuzzer: `K0_FUZZ_ITERS=5000000 cargo test --release --offline --target "$(rustc -vV | sed -n 's/^host: //p')" -p k0-boot fuzz -- --nocapture`. A failing case prints `K0_FUZZ_CASE=0x...`, which replays it and dumps the input. The fuzzer's DTB builder in `crates/k0-boot/src/fdt/builder.rs` is a convenient way to write a crafted DTB for a reproducer. `k0-efi` has three more deterministic fuzzers (`fuzz_plan_with_random_maps`, `fuzz_rewrite_with_mutated_trees`, `fuzz_prepare_end_to_end`) with the same `K0_FUZZ_ITERS`, `K0_FUZZ_SEED` and `K0_FUZZ_CASE` variables: run them with `-p k0-efi fuzz`. The unit tests of `k0-efi` use measured firmware memory maps as vectors; a crafted memory map or firmware DTB is the natural reproducer for the loader.
- PAC, PAN and RNDR paths: the default `cortex-a72` model has none of them. `tools/qemu-boot-test.sh target/aarch64-unknown-none-softfloat/debug/k0-kernel -cpu max` (an image built with `--features console`) boots on a CPU that has all three.
- A boot that the kernel refuses before it has a console prints nothing, and an image without a console feature prints nothing on the serial port at all. The reason is in the boot log in memory: start QEMU with `K0_QEMU_MONITOR=<socket path>` and read it with `tools/boot-log.py <elf> <load address> <socket path>` (the load address on QEMU `virt` is `0x40080000`).
- Debugging: append `-s -S` to the runner (`tools/qemu-virt-runner.sh <elf> -s -S`) and attach with `gdb-multiarch target/aarch64-unknown-none-softfloat/debug/k0-kernel -ex 'target remote :1234'`. `-d int,guest_errors` prints exception traces. `llvm-objdump -d` (from the pinned toolchain, linked into `/usr/local/bin`) disassembles both images.
- Fault semantics: an EL0 fault prints `k0: task fault <name> (esr .. elr .. far ..), killing task` and kills only that task. A kernel-internal exception goes to `exception_fatal`, which halts the machine on purpose (fail-secure). Reaching that halt from EL0 is a finding.

## How we rate severity

Rate by what EL0 code can do to EL1 or, on the current `main` branch, to another confined task (see "Anything to leave alone").

- **Critical**: any EL0 -> EL1 privilege escalation, and on the current `main` branch any break of task isolation (reading or writing another task's memory, using a slot or capability of another task, a revoked capability or stale mapping that still works). Executing attacker-chosen code at EL1; reading or writing kernel memory or arbitrary physical memory through a system call; obtaining a mapping, capability or object that the caller's slot arguments do not grant (bypassing a capability or permission check); mapping memory that is both writable and executable for EL0, or kernel memory into TTBR0; getting the kernel to restore EL1 state (mode, exception level, interrupt masks) that came from user input.
- **High**: memory-safety bugs in kernel code reachable from EL0, with or without a demonstrated exploit (out-of-bounds index, integer overflow or truncation in size or address arithmetic, stale raw pointers, aliasing `&mut`, unsound `unsafe`); a system call or fault sequence that halts the whole system (kernel panic, `exception_fatal`, an unbounded loop with interrupts masked, or a scheduler that cannot continue); missing TLB or cache maintenance that lets a task keep using memory after it was unmapped or retyped; kernel register or memory contents leaking to EL0 (registers not restored or cleared on the return path, uninitialised memory handed out by `retype` or `map`); checks that a race between the timer interrupt and a system call can bypass.
- **Loader findings** are rated by what the kernel ends up trusting. **Critical**: a memory map or firmware device tree that makes the loader pass the kernel a RAM range that includes memory firmware still uses (runtime or boot services memory, MMIO, a reservation) so that it can reach user space, or that makes the loader start a kernel image that fails its own check. **High**: memory-safety bugs in the loader, a refusal that is skipped (the loader boots on input it should refuse), or an `ExitBootServices` path that leaves the system in an undefined state. **Medium**: a panic or an overly cautious refusal on a valid map, a leak of memory the loader should have wiped, a plan that loses RAM beyond the stated policy. Findings that need hostile firmware are Low (see "Anything to leave alone").
- **Input findings** are rated by what an outside party on the serial line gains. **Critical**: a byte stream or timing that gives code execution or memory access at EL1, or that makes a task do more than the operator's four operations. **High**: a stream that halts the machine or lets kernel work in interrupt context grow without the reader's bound; a wake-up or a byte delivered to a task that does not hold the read right. **Medium**: a stream that wedges the terminal or the input path until reboot. The lack of authentication on the serial line and the operator's power to erase the key are known (see "Anything to leave alone").
- **Medium**: malformed DTB input that panics, reads out of bounds, produces an unsafe memory map or gets a device mapped over memory that is handed out (the boot chain is trusted, so cap these at Medium unless they give code execution); exhaustion of kernel resources (for example untyped memory, TCB or endpoint objects; the kernel page tables and the address space registry are reserved at boot and no longer run out) by a single task that denies service to others without halting the kernel; scheduler starvation; mistakes in `write_bootinfo` beyond the known physical address exposure.
- **Low**: problems that need a misbehaving root task to trigger; `build.rs` issues with trusted source inputs; console formatting and diagnostic wording; hardening that is missing but has no exploitable consequence today.
- A root-cause analysis plus a patch is welcome at every level. A reproducer counts for more than a severity argument.

## Report and patch format

- State the commit hash (`git -C /src rev-parse HEAD`), the platform (QEMU virt unless stated) and the exact system call sequence or root-task patch that triggers the issue. Include the console lines around the failure; the `esr`, `elr` and `far` values are the most useful part.
- Prefer a reproducer as a diff against `userspace/root-task/src/main.rs` that prints a distinctive line on success.
- Patches should be Rust against the current `main`, add no new third-party dependencies, keep fail-secure behaviour (reject or halt rather than guess) and prefer checks that the compiler or `const` assertions can enforce. Every `unsafe` block in this codebase carries a `// SAFETY:` note; keep that. Existing comments are in Korean; English comments in a patch are fine.

## Anything to leave alone

These are known, tracked in `SECURITY.md`, and are not new findings:

- No isolation between tasks in `v0.1.0` and earlier commits: one static root CNode, one address space, no capability derivation tree, no `MINT`, no `revoke`, no capability transfer over IPC (GHSA-vmpv-qc49-3p6r). Findings that only apply to those versions are not new. The current `main` branch (unreleased) has per-task CNodes and address spaces, rights, badges, a derivation list and revocation, so isolation bypasses there ARE in scope. EL0 reaching EL1 memory is always in scope.
- Known limits of isolation on `main`: no fault delivery to a handler, no notifications, no capability transfer over IPC, a single core, and a sender already queued on an endpoint still delivers once after its capability is revoked. Availability is not protected in general (see below). New executable code cannot be loaded after boot by design, so a confined task runs code from the root task image.
- Availability limits (GHSA-q99x-2wrv-358p is still listed as affecting 0.1.0 and earlier, with no fixed version; `main` contains a change that addresses its subject). The kernel no longer halts when every task is blocked: it idles and prints `k0: idle (waiting for a timeout)` or `k0: all tasks stopped (none ready, no timeout pending)` once. A task can bound its own waits with the timeout in the upper 32 bits of `x1` (scheduler ticks of 1 second; `TIMEOUT`, `REPLY_TIMEOUT`, `BAD_FLAGS`). Still known: a wait without a timeout can last forever if the partner never acts; a timeout says when a task becomes ready, not when it runs (round-robin with a tick of one second, no priority or CPU budget, so a task with `Untyped` memory can dilute everybody's share by creating tasks, which stays known); the kernel is not preemptible, so a long system call such as `CAP_REVOKE` on an `Untyped` with many objects delays every task and every timeout; `k0_arch::fatal`, a kernel panic and an SError from EL0 stop the machine; fault and exit lines can fill the kernel part of the boot log.
- Scheduler timing, addressed on `main`: taking the CPU from the next task by calling `YIELD` (no capability needed) or blocking just before the tick. A task that gets the CPU between two ticks is no longer preempted by the first tick it meets (`crates/k0-slice`, used by `on_tick` and `resume_from_idle` in `crates/k0-sched`), so it is not cut before it has run one full period, and with N ready tasks a task that never yields or blocks keeps at least 1/N of the CPU. This was checked by search in a model (up to 6 tasks) and by host tests, not proven, and a self-test at every boot (`root: slice test yield pass`, `root: slice test block pass`) covers the kernel's use of it. A report that breaks this is still welcome. Known limits that stay: the share has no budget and N grows with every task created; the timing channel through the scheduler is open (a task changes when, and for how long, another task runs by choosing when to yield or block, and this has not been analysed); there is no latency promise (a task that becomes ready can wait up to one tick longer than before); three connections of the rule to the scheduler (the tick's own switch, the idle loop's report of a tick, the entry kind at the hand-off to the root task) are covered only by the host model and by no test on the real kernel, so a report that one of them is wrong is still welcome, as a latency finding; the measurements ran in QEMU only, with an attacker whose yield point was set for it.
- EL0 still cannot read a hardware counter or timer. Timeouts give it a clock as coarse as the scheduler tick; whether that can be amplified into a timing source for cache or speculation attacks has not been analysed.
- The kernel tables are sized at boot: alias page tables and address space entries are reserved from the top of every range handed out as `Untyped` (`k0: kernel reserve ...` line), so `RETYPE` no longer fails with `KERNEL_RESOURCE` for lack of tables and the number of address spaces is limited only by memory. The 40-table static pool is used only during boot.
- DTB memory regions are not bounded by the physical address width (GHSA-hj3f-38h9-hrpj). The current `main` branch stops the boot on such a region; the advisory itself is still a draft.
- No KASLR: the kernel image always sits at the same virtual address. `write_bootinfo` exposes the physical addresses of `Untyped` regions to the root task.
- A wrong or hostile DTB can stop the boot, or point the console at another device that passes the checks (a 16550 and an SBSA UART have no identification register). An image without a console driver never maps or writes the console page, but it still refuses a device tree whose console node fails the checks. A pinned build (`K0_PIN`) compares values that come from the DTB, so it does not stop a hostile boot chain.
- Signing oracle limits, all in `SECURITY.md` under "The signing oracle": the Ed25519 implementation is unvalidated and the key does not come from an approved random bit generator; no side-channel analysis; one key shared by all signers, one key per boot; no persistence, import, export or DRBG; the availability of the vault is not protected; the root task is trusted and could read the vault; only run in QEMU. The kernel zeroes the `rng-seed` and `kaslr-seed` bytes in the DTB once, right before it enters the root task; copies kept by firmware or the loader and live boot stack frames are not wiped.
- Serial input limits, all in `SECURITY.md` under "Serial input and the operator terminal": there is no authentication on the serial line, and the operator can erase the key (denial of service by design) but cannot sign, deliver a seed or change policy; the receive code runs at EL1 and a user-space driver would need device and interrupt delegation, which K0 does not have; an outside party can cause interrupts while tasks run (bounded by the reader), the reader learns arrival times finer than the tick and other tasks can notice the stolen time, a timing channel that has not been analysed; input waits behind running tasks (no priorities, up to a tick per ready task, plus one more when the running task got the CPU between two ticks); a 16550 console has no input; the SBSA UART path, FIFO overruns, the receive timeout interrupt and the cut-off of an interrupt line without a UART cause are covered only by host tests with a fake UART; no test measures kernel time under a flood on a machine; "dropped before the prompt" counts bytes that reached the UART, and an emulator that holds bytes back delivers them later; a kernel line that appears while the operator types splits the screen line but not the buffer; the terminal can erase within its current line; no signing client exists in service mode; the terminal and the vault are not restarted if they die; terminal output counts against the user share of the in-memory boot log. Nothing ran on real hardware.
- The DTB pointer in `x0` is mapped read-only and read before any memory map exists. A boot loader that passes the address of a device makes the kernel read device registers as memory.
- A task with a `Console` capability that has the write right can print lines that look like kernel output (`k0: ...`), in the boot log and, in an image with a console driver, on the console. Its output is filtered for control bytes (only a capability with the read right may also emit backspace) but not marked. That includes the `k0: console drivers [...]` line, so only its first occurrence, or the image file, identifies a build.
- Optional console output: an empty serial log shows only that no byte reached the serial port of QEMU virt (a PL011), not that no register was read; the symbol check runs on debug images and release (LTO) images without console are not booted; no image without console is booted through UEFI; the boot log in kernel memory is readable by anyone who can read RAM or attach a debugger. See "Optional console output" in `SECURITY.md`.
- A trap to EL2 after the kernel has dropped to EL1 parks the whole machine by design.
- PAC keys are shared between EL0 and EL1. No `pac-ret` code generation is enabled yet, so there is nothing to forge today.
- FP/SIMD is trapped at EL0 on purpose (`CPACR_EL1 = 0`); a task that touches a SIMD register is killed by design.
- `exception_fatal` halting on a kernel-internal exception is intended fail-secure behaviour. Only an EL0-reachable path into it is a finding.
- The root task is trusted; its image is embedded and hashed, not signed. Kernel image integrity belongs to the boot chain.
- The UEFI loader's known limits, all in `SECURITY.md` under "The UEFI loader": hostile firmware is not defended against, only wrong firmware; the SHA-256 of the embedded kernel is a corruption check and not a signature (only the firmware's Secure Boot gives authenticity); only this loader may start the kernel under UEFI, since a generic loader that passes the firmware device tree through hands firmware memory to user space; a refusal returns to the firmware unless the loader was built with `refuse-halt`; the cache flush and MMU-off sequence cannot be tested under QEMU (TCG has no caches) and is checked only for presence by `tools/pe-check.py`; a pinned build under UEFI is untested; a device left running by firmware can still write to memory (no IOMMU); the loader's entropy stays readable in the device tree in memory; the kernel never calls UEFI runtime services; firmware that types device registers as `EfiReservedMemoryType` or gives one malformed descriptor makes the loader refuse (fail closed); the block re-placement and free-on-refusal paths were not exercised; the loader file is not bit-for-bit reproducible across build directories. About 23 to 32 MiB of boot services memory is left unused on purpose. Firmware with neither a device tree nor ACPI static tables is refused. The ACPI path reads only the static tables (RSDP, XSDT, MADT, GTDT and SPCR, never AML) and has been booted only on QEMU virt.
- Real boards, U-Boot's EFI implementation, Raspberry Pi UEFI, firmware other than EDK2 `ArmVirtQemu`, and KVM have never been booted under UEFI either; do not report "untested on hardware".
- Only QEMU runs in this image. Real boards, KVM and other hypervisors, the 16550 console driver (no test has executed it, and it has no input path), the SBSA UART and CPUs with `HCR_EL2.E2H` fixed to 1 have never been booted. Review of those paths is welcome; do not report "untested on hardware".
- Upstream issues in vendored crates that are not reachable from the kernel's SHA-256 use.
