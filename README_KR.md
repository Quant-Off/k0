# K0

<div align="center">

[English](README.md) | 한국어

</div>

AArch64 대상 마이크로커널입니다. seL4 방식의 케이퍼빌리티 자원 모델을 따르고 Rust `no_std`로 작성됐습니다. 커널에는 heap이 없습니다. 남는 물리 메모리 전부를 untyped 케이퍼빌리티로 첫 사용자 태스크에 넘기고, 부팅 이후 생기는 커널 오브젝트는 전부 그 태스크가 retype한 메모리 안에 자리 잡습니다. 그 밖의 커널 상태는 고정 크기 정적 저장소(커널 자체 매핑용 페이지 테이블 32장 풀, 항목 256개짜리 주소 공간 레지스트리(0번 항목은 미사용), 스케줄러 상태)뿐입니다. 1차 타겟은 QEMU virt(4K 그래뉼)와 Apple Silicon(16K 그래뉼)이고, AMD64를 비롯한 다른 아키텍처는 1차 타겟 완료 후 확장 대상입니다. 현재 크레이트 버전은 정식 릴리스 전 단계인 0.1.0이고, 현재 `main` 브랜치는 릴리스되지 않았으며 0.1.0 태그보다 앞서 있습니다. 커널 쪽 코드는 주석을 포함하고 테스트를 제외해 Rust와 어셈블리 약 7,400줄이라 여전히 처음부터 끝까지 읽을 수 있는 분량입니다.

## 보안 상태

릴리스된 v0.1.0 태그는 태스크 간 격리를 제공하지 않습니다. 그 태그에서 만든 태스크는 루트 태스크의 스레드이며, 게시된 어드바이저리는 그 태그에 그대로 적용됩니다.

현재 `main` 브랜치(미릴리스)는 태스크를 격리합니다. 태스크는 구성될 때 CNode 하나와 주소 공간 하나에 묶이고, 서로 다른 것에 묶인 태스크끼리는 격리됩니다(루트 태스크의 보조 스레드처럼 같은 것을 함께 쓰는 태스크끼리는 격리되지 않습니다). 슬롯 번호는 호출한 태스크 자신의 CNode 안에서만 의미가 있으며, 케이퍼빌리티를 revoke하거나 delete하면 거기서 파생된 것이 전부 사라집니다. 설계가 제공하고 테스트가 확인하는 것은 다음과 같습니다. 격리된 태스크는 자신이 케이퍼빌리티를 갖지 않은 오브젝트를 가리킬 수 없고, 그 태스크의 `AddrSpace` 케이퍼빌리티를 가진 쪽이 주소 공간에 매핑해 준 메모리에만 접근합니다. 태스크의 TCB, CNode, AddrSpace 케이퍼빌리티를 가진 쪽이 그 태스크를 통제합니다. 제공하지 않는 것은 **가용성**입니다. 격리된 태스크도 마지막으로 블록해 모든 태스크를 멈추게 하거나, 정적 커널 페이지 테이블 풀이나 주소 공간 레지스트리를 고갈시켜 시스템을 굶기거나 멈출 수 있습니다. 여기서 격리는 메모리와 케이퍼빌리티에 한정됩니다. 16K(Apple) 빌드는 컴파일과 호스트 테스트만 했고 부팅해 보지 않았습니다. 신뢰하지 않는 코드를 K0 위에서 실행하는 것은 실험적인 용도로만 보고, 서비스 거부가 문제되는 환경에서는 실행하지 마세요. 격리 모델, 알려진 어드바이저리, 신고 방법은 [SECURITY_KR.md](SECURITY_KR.md)([English](SECURITY.md))를 참고하세요.

## 지금 동작하는 것

- **부팅**: Linux arm64 Image 헤더로 QEMU와 m1n1에서 적재됩니다. 부트 코어 하나만 진행하고, EL2로 들어오면 EL1으로 내려가며, 지원하지 않는 진입 상태는 파킹합니다.
- **메모리**: 커널 매핑은 W^X이고 `SCTLR_EL1.WXN`이 켜져 있습니다. 부트 스택 아래 가드 페이지, higher-half 별칭, AT 명령을 이용한 부팅 시 자가 검사가 있습니다.
- **신뢰하지 않는 부트 입력**: DTB는 적대적 입력으로 파싱하고, 메모리 맵이 커널 MMIO 창과 겹치면 부팅을 거부합니다.
- **하드닝**: CPU가 지원하면 PAC 키를 파생해 넣고 PAN을 켜며, EL0에 노출되는 카운터, 디버그, PMU 접근을 막습니다. 현재 stable 컴파일러는 포인터 인증 명령을 만들지 않으므로 커널 복귀 주소는 아직 서명되지 않습니다.
- **케이퍼빌리티**: untyped 메모리, `Frame` / `PageTable` / `TCB` / `Endpoint` / `CNode` / `AddrSpace`로의 retype, 케이퍼빌리티로만 대상 주소 공간을 정하는 `MAP`과 `UNMAP`. 케이퍼빌리티는 권한(읽기, 쓰기, 실행)을 갖고, 엔드포인트 케이퍼빌리티는 배지를 가질 수 있으며, `CAP_COPY`와 `CAP_MOVE`로 슬롯 사이를 옮깁니다.
- **태스크와 스케줄링**: 태스크를 CNode와 주소 공간에 묶는 `TCB_CONFIGURE`, `TCB_RESUME`, `YIELD`, `EXIT`, 타이머 선점이 있는 라운드 로빈.
- **IPC**: 레지스터로만 메시지를 옮기는 동기 랑데부 `SEND` / `RECV` / `CALL` / `REPLY_RECV`. 보내려면 엔드포인트 케이퍼빌리티의 쓰기 권한이, 받으려면 읽기 권한이 필요하고, 수신자는 송신 케이퍼빌리티의 배지를 받으며, 응답 자격은 1회성입니다.
- **폴트 격리**: EL0 폴트, 알 수 없는 시스템 콜, `EXIT`는 시스템 전체가 아니라 그 태스크만 종료합니다.
- **태스크 격리와 revoke**: 모든 태스크는 구성 때 묶인 CNode와 주소 공간으로 실행되며, 서로 다른 것에 묶인 태스크끼리는 격리됩니다. 케이퍼빌리티는 파생 목록을 이루고, `CAP_REVOKE`와 `CAP_DELETE`는 대상에서 파생된 케이퍼빌리티를 전부 제거하며, 원본 케이퍼빌리티가 사라지는 오브젝트의 매핑을 해제하고 종료 처리하고, CNode나 주소 공간을 잃은 태스크를 정리하고, untyped 메모리를 매번 0으로 지워 다시 retype할 수 있게 합니다. 어떤 프레임도 한 곳에서는 쓰기 가능이고 다른 곳에서는 실행 가능인 일이 없습니다.
- **루트 태스크 무결성**: 내장 루트 태스크 이미지를 부팅 때 SHA-256으로 다시 검사합니다. 이것은 손상 검사이지 서명 검증이 아닙니다(이유는 [SECURITY_KR.md](SECURITY_KR.md)의 범위 절 참고).

위 항목은 전부 루트 태스크가 부팅할 때마다 자가 테스트로 확인합니다.

## 아직 없는 것

- IPC를 통한 케이퍼빌리티 전송(Grant)
- IRQ를 사용자 공간에 전달하는 Notification 오브젝트
- EL0 폴트를 핸들러 태스크에 IPC로 전달
- 타임아웃, 그리고 멀티 코어
- 가용성 보장: 모든 태스크가 블록되면 커널은 여전히 코어를 파킹하고, untyped 메모리를 많이 쥔 태스크가 커널 페이지 테이블 풀이나 주소 공간 레지스트리를 고갈시킬 수 있음
- 부팅 이후의 새 실행 코드 적재: 실행 가능 프레임은 루트 태스크 이미지에만 있으므로 격리된 태스크는 그 이미지의 코드를 실행함
- 다단계 케이퍼빌리티 조회와 하드웨어 ASID(케이퍼빌리티 공간은 단일 단계이고 `TTBR0`가 바뀌면 TLB 전체를 비움)
- 케이퍼빌리티를 revoke해도 이미 엔드포인트 큐에 있는 송신자는 취소되지 않고 한 번은 전달됨
- 루트 태스크가 분리 배포되는 시점의 Ed25519 공개키 검증
- Apple Silicon 실기 부팅 검증(현재는 빌드와 호스트 테스트만 검증)
- AMD64 등 다른 아키텍처

## 빌드와 실행

```sh
cargo virt    # QEMU virt에서 부팅
cargo apple   # Apple Silicon(m1n1) release 빌드
```

`rustup`, 펌웨어 ROM을 포함한 `qemu-system-aarch64`, 호스트 C 컴파일러가 필요합니다. 의존성은 전부 vendor 디렉터리에 들어 있어 빌드에 네트워크가 필요 없습니다. 자세한 준비 과정은 [CONTRIBUTING_KR.md](CONTRIBUTING_KR.md)에 있습니다.

## 테스트

```sh
tools/host-test.sh                  # 호스트 단위 테스트와 DTB 퍼징
cargo build -p k0-kernel --offline
tools/qemu-boot-test.sh             # QEMU 부팅과 루트 태스크 자가 테스트 확인
```

호스트 테스트에는 무작위 retype, copy, move, delete, revoke 순서에 대한 케이퍼빌리티 파생 목록의 모델 테스트와 두 그래뉼 모두에 대한 사용자 페이지 테이블 워커 테스트가 들어 있습니다. 부팅 자가 테스트는 격리된 태스크를 만들어 서로의 메모리와 케이퍼빌리티에 닿지 못하는지, 태스크를 모든 상태에서 삭제할 수 있는지, revoke된 untyped 메모리를 다시 retype할 수 있는지 확인합니다.

CI는 x86-64와 AArch64에서 네트워크를 끊은 컨테이너 안에 같은 테스트를 돌리고, 매주 더 긴 퍼징을 실행합니다.

## 저장소 구조

| 경로 | 내용 |
| --- | --- |
| `kernel/` | 커널 바이너리. 부트 어셈블리, 초기화 순서, 시스템 콜 정책(`syscall.rs`), 케이퍼빌리티 제거 시 오브젝트 종료 처리(`object.rs`), 링커 스크립트 |
| `crates/k0-abi` | 사용자 공간과 공유하는 시스템 콜 번호, 에러 코드, bootinfo 레이아웃 |
| `crates/k0-arch` | 예외 벡터, EL0 진입과 복귀, GICv3와 타이머, PAC과 PAN, 초기 콘솔 |
| `crates/k0-boot` | DTB 파서, 루트 태스크 이미지 내장과 무결성 검사, PAC 키 파생 |
| `crates/k0-cap` | 케이퍼빌리티 슬롯과 권한, CNode, 파생 목록, untyped 메모리, retype, revoke와 delete |
| `crates/k0-mm` | 커널 페이지 테이블, MMU 활성화, 사용자 주소 공간과 주소 공간 레지스트리 |
| `crates/k0-task` | 자기 CNode와 주소 공간에 묶인 TCB, 엔드포인트, 루트 태스크 적재 |
| `crates/k0-sched` | 라운드 로빈 스케줄러 |
| `crates/k0-ipc` | 동기 IPC |
| `userspace/root-task` | 첫 사용자 태스크와 자가 테스트 |
| `tools/` | QEMU 러너, 부팅 테스트, 호스트 테스트 |
| `vendor/` | vendor 처리한 서드파티 크레이트(`sha2`와 그 의존성) |
